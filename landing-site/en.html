Who it is for

For a few servers and a small team

Plain Docker and Compose, no Kubernetes or Swarm. For a team where people need different levels of access.

Every server in one place

See every server and container in the panel instead of SSHing into each one.

Secrets in git, encrypted

Configuration and passwords live in one repository. Nothing is stored in plain text.

Exactly the access people need

Let someone restart one service on one server without giving them the whole server.

Restart from your phone

A service crashed and your laptop is far away? One command in Discord, with the same permissions as in the panel.

Features

What container-forest does today

It has run real production infrastructure since October 2026. Until 1.0, a minor release may include breaking changes; the changelog lists them.

Agents

One per server, enrolled with a one-time token. The agent connects out to the central service, so a server can sit behind NAT with no open ports.

Containers

State and logs of every container; start, stop, restart. Compose projects started on a server by hand show up too, and you can manage them.

GitOps

Deploy from a public or private repository by hand, on push or from CI. Every deployment records its commit, and stacks can require signed commits.

Rollback

Roll a stack back to a commit it deployed before. It stays there until you tell it to follow the branch again.

Secrets

SOPS with a separate age key per server or per stack. With the forest git filter you edit secrets in plain text in your clone and commit them encrypted.

Explicit actions

restart, redeploy, redeploy with pull and down are separate actions, not one "update" button.

Image updates

Per-stack image policies: the service notices new image versions and commits the new tag to the stack's repository.

Resource usage

CPU, memory, network, disk and process graphs for containers, stacks and servers, with alerts on high usage. The same numbers in the CLI and the bot.

Access control

Roles on a server or on a single stack, a compose policy per server (what stacks may mount and run) and an audit log.

Sign-in

Password, passkeys or Discord. Two-factor authentication with an authenticator app, which an administrator can require for everyone.

Discord bot

Commands, menus and notifications: deployments, crashed containers, agents going offline, high usage. Same permissions as the panel.

forest CLI

Browser sign-in and scoped personal API tokens (read-only, selected servers, expiry). Everything the panel can do.

Panel

English and Ukrainian, with live updates. Works on a phone, installs as an app and has five colour themes.

Backups

Backups of the central service to S3-compatible storage, encrypted to an offline key.

One entry point

The panel, the API, the agents and the bot all use one domain on port 443. Caddy gets the certificate itself.

Architecture

The agent calls home

Every server runs an agent. It connects out to the central service and keeps a gRPC stream open to it.

No open ports

The Docker API is never exposed to the network. Servers can sit behind NAT, because the agent always opens the connection.

Only known commands

The agent runs a fixed set of typed commands defined in Protocol Buffers. There is no "run any shell command".

Permissions live in the centre

Secrets, policies and permissions are stored and enforced only by the central service. The panel, the bot and the CLI just hide what you cannot do.

SOPS + age

A password in git that nobody can read

Secrets are encrypted with a separate key for every server or stack. Only the central service decrypts them, right before a deployment. An Editor sees them in plain text in their own clone thanks to the forest git filter.

Roles

Access to a server or to one stack

A role is granted on a whole server or on a single stack; on a stack the higher of the two applies. Only a system administrator appoints a server administrator, and only on a whole server.

An Editor on a server effectively has root on the host: a compose file can mount / or run a privileged container. The compose policy limits what stacks may do, but grant this role with care anyway.

Themes

Five themes, each light and dark

The default is forest. The seasonal backdrop shows young leaves in spring, butterflies and poplar fluff in summer, falling leaves in autumn, snow in winter, or rain all year. It covers nothing and can be turned off.

Quick start

Up and running in minutes

You need a host with Docker and a DNS name pointing to it (ports 80 and 443 reachable) for the central service, and Docker on every server you want to manage.

  1. Run the aggregator and the panel on the central host

    mkdir -p /srv/container-forest && cd /srv/container-forest
curl -fsSLO https://raw.githubusercontent.com/container-forest/container-forest/main/deploy/aggregator/compose.yaml
cat > .env <<'EOF'
CF_DOMAIN=forest.example.com
CF_BOOTSTRAP__ADMINUSERNAME=admin
CF_BOOTSTRAP__ADMINPASSWORD=change-me-to-12+-chars
EOF
chmod 600 .env
docker compose up -d

    Caddy gets a Let's Encrypt certificate for CF_DOMAIN. Sign in at https://forest.example.com, then remove the two CF_BOOTSTRAP__* lines.

  2. Add a server

    In the panel, open Environments → New environment. It shows a one-time enrollment token and a ready compose.yaml for the agent. Run it on that server with docker compose up -d, and the server goes online in the panel.

  3. Deploy a stack

    Add a git repository (for a private one, first add a git connection with a read-only token), then create a stack: repository, branch and path to compose.yaml. Press Deploy, or turn on deploy on push.

  4. Optional: the CLI and the Discord bot

    Download forest for Linux, macOS or Windows from the latest release and sign in:

    forest login https://forest.example.com
